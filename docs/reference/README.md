# Reference

Lookup tables. Where the rest of `docs/` explains how something works, this directory
enumerates: every entity, every verb, every NetObject prefix, every status code, every SWQL
function. The pages are long on purpose, because the question they answer is "does this
exist and what is it called", and a partial answer to that is worse than none.

Most of what is here is **generated from `data/`**. One page, [glossary.md](glossary.md),
is written by hand.

## The generated pages are not to be edited

Five pages are produced by [`tools/build_reference_docs.py`](../../tools/build_reference_docs.py)
from the extracted schema and reference data. Each carries a banner saying so:

```text
<!-- GENERATED FILE. Do not edit by hand.
     Produced by tools/build_reference_docs.py from data/schema/2026.2/.
     Regenerate with: make docs-reference -->
```

An edit to one of them is overwritten by the next build, and CI regenerates and diffs, so a
hand edit fails the build the way a stale lockfile would. **Fix the generator instead.**
That is usually the better fix anyway: correcting the code corrects every row rather than
the one you noticed.

The reason these are generated rather than written is arithmetic. A hand-maintained table
of 2067 entities drifts from the schema the first time anyone touches it, and a reference
that might be stale is worse than no reference at all. Generation also means the whole set
re-derives from one command when the documented platform version changes.

## Reading a whole page is rarely the fast path

Each page is an enumeration, which makes it the right tool for browsing, for diffing, and
for answering "what else is there". For a single lookup, the offline query tool is faster
and gives you more per answer. Both read the same `data/`, so they cannot disagree.

### entity-index.md

Every entity with its base type, its declared operations, and counts of properties,
relationships and verbs. The `Ops` column abbreviates the operations by first letter, and
it is the column to read first: an entity without `c` cannot be created through CRUD no
matter how the request is shaped.

For one entity in full, including the inheritance chain, every property with its type, both
relationship tables and every verb:

```bash
python3 tools/schema_query.py show Orion.Nodes
```

When you only remember part of the name, which is the more common case:

```bash
python3 tools/schema_query.py find volume capacity --properties
python3 tools/schema_query.py children System.ManagedEntity
python3 tools/schema_query.py path Orion.APM.Component Orion.Nodes
```

The narrative counterpart is [../schema/entity-model.md](../schema/entity-model.md), and
[../schema/key-entities.md](../schema/key-entities.md) covers the entities you will
actually use in depth.

### verb-index.md

Every verb with its positional signature, return type, the right it requires and a summary.
A `?` after a parameter name marks it optional. This is the page to scan when you want to
know what a module lets you do, and the one to search when a verb name appears in a script
you inherited.

For one verb, which also prints ready-to-paste PowerShell and REST call syntax:

```bash
python3 tools/schema_query.py verb Orion.Nodes Unmanage
```

```text
Orion.Nodes.Unmanage
  Set the given node into maintenance mode so the node polling is disabled
  returns: System.Void
  REST:    POST /Invoke/Orion.Nodes/Unmanage
  requires: allowUnmanage
  parameters (5):
    netObjectId: string (required)
    unmanageTime: string (required)
    remanageTime: string (required)
    isRelative: boolean (required)
    allowOverlapping: boolean (optional)
```

Or every verb on an entity, or every verb whose name matches something:

```bash
python3 tools/schema_query.py verbs --entity Orion.Nodes
python3 tools/schema_query.py verbs --grep unmanage
```

Arguments are positional and the names never travel on the wire, so the order in the
signature is the entire contract. The narrative counterpart is
[../swis/invoke-verbs.md](../swis/invoke-verbs.md), and
[../swis/verb-catalog.md](../swis/verb-catalog.md) is the curated shortlist by task.

### netobject-types.md

Entity to NetObject prefix, key properties and parent entity, grouped by module, with rows
that no longer resolve in 2026.2 marked in a Status column. This is the table you need
whenever a verb takes a `netObjectId`, because node 42 is `N:42` and a bare `42` is
accepted and acts on nothing.

`schema_query.py` reads `data/schema/` only, so it does not cover this table. The
equivalent single lookup is `jq` against the reference data:

```bash
jq -r '.[] | select(.entity=="Orion.Volumes") | "\(.netObjectPrefix)\t\(.keyProperties|join(","))"' data/reference/netobject-types.json
```

```text
V	VolumeID
```

The prefix is stored without its colon, so the string a verb wants for volume 9 is `V:9`.

The narrative counterpart is [../schema/netobject-types.md](../schema/netobject-types.md),
which explains what the prefix is for and where it is required.

### status-codes.md

Status id, name, rank and meaning, plus the two queries most reports need. Rank is the
column people misread: **lower is worse**, because rollup takes the child with the lowest
rank, which is why Down (110) beats Warning (220).

```bash
jq -r '.[] | select(.status==9) | "\(.status)\t\(.name)\trank \(.rank)"' data/reference/status-codes.json
```

```text
9	Unmanaged	rank 499
```

Do not hard-code these numbers into a report. `Orion.StatusInfo` is the lookup table on a
live server, and joining it keeps the query correct if SolarWinds adds a status. The
narrative counterpart is [../schema/status-codes.md](../schema/status-codes.md).

### swql-function-index.md

Every SWQL function with its signature, the version it is attested from, a description and
a worked example. Functions marked with a warning symbol are attested only by a community
workbook rather than by the official reference, which is exactly the set worth checking
against your own server before depending on one.

```bash
jq -r '.[] | select(.documented | not) | "\(.name)\t\(.source)"' data/reference/swql-functions.json
```

```text
ChangeTimeZone	community workbook
```

The narrative counterparts are [../swql/functions.md](../swql/functions.md) and
[../swql/date-and-time.md](../swql/date-and-time.md), which is where the functions that
quietly return wrong answers are explained.

## The written page

### glossary.md

[glossary.md](glossary.md) defines the vocabulary: SWIS, SWQL, entity, verb, NetObject,
element, rollup, unmanaged, the module acronyms and the three product names. It is written
rather than generated because a definition is a judgement about what a reader needs, not a
projection of a data file, and because most of these terms have no single field in `data/`
to derive from.

It is held to the same standard as the rest of the documentation: every entity, property
and verb it names was looked up first, and `make check` verifies those names on every
build.

## Two more generated pages

These come from different generators, so they are worth naming separately.

### unverified.md

[unverified.md](unverified.md) is generated by
[`tools/build_unverified_index.py`](../../tools/build_unverified_index.py) from **the
documentation itself**, not from `data/`. It scans every authored page for the phrasings
this repository uses to hedge a claim and collects them in one place, so the honest
admissions scattered across sixty pages become a single list of where the edges are.

That makes it the one generated page whose content changes when you edit prose. If your
change adds, removes or rewords an unverified statement, regenerate it in the same commit
with `make docs-reference`.

### schema-changes-*.md

The upgrade impact reports, generated by
[`tools/diff_schema.py`](../../tools/diff_schema.py) from two extracted versions:

```bash
make schema-diff FROM=2025.4 TO=2026.2
```

Read the removals first. Additions cannot break code that already works; removals can, and
so can a verb whose positional arguments were reordered, which is the worst category
because an existing call still has the right number of arguments and sends them into the
wrong slots.

## Regenerating everything

```bash
make data                    # rebuild data/ from the OrionSDK docs (VERSION=2026.2)
make docs-reference          # regenerate the pages in this directory
make check                   # validate queries, names, counts, signatures and links
```

`make data VERSION=2025.4` documents a different release. The generated pages carry the
version in their banner and in their opening sentence, so a page and its data cannot drift
apart silently.

## When the answer is not here

This directory documents one platform version, and the schema varies with the release and
with which modules are licensed and installed. For a specific server, that server is the
authority, and it will answer the same questions through the `Metadata.*` entities:

```sql
SELECT FullName, BaseType, CanCreate, CanUpdate, CanDelete, CanInvoke
FROM Metadata.Entity
WHERE FullName LIKE '%Interface%'
ORDER BY FullName
```

```sql
SELECT Position, Name, Type, IsOptional
FROM Metadata.VerbArgument
WHERE EntityName = 'Orion.Nodes' AND VerbName = 'Unmanage'
ORDER BY Position
```

[../swis/metadata-introspection.md](../swis/metadata-introspection.md) covers the whole
namespace, and [../guides/building-integrations.md](../guides/building-integrations.md)
shows how to use it to feature-detect at runtime instead of hard-coding a version check.
